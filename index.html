1 · Foundations

Chat vs. agent

agent = LLM + tools + a loop + a goal (+ a reason to stop)
Left: you are the loop — you run things and paste results back. Right: the model is given tools and runs the loop itself until the goal is met. Step 3: the dot is the loop running — keep it spinning while you talk. That's the whole idea; everything else is detail.
1 · Foundations

Under the hood: next-token prediction

Stateless. Each call starts from zero. The model's only "memory" of your task is the text sent with that call.

Frozen at training time. It writes what's plausible, which explains hallucinated APIs and outdated library calls.

Keep it to 90 seconds. Text → tokens → a probability distribution → pick one → append → repeat. Two consequences matter for the rest of the talk: (1) stateless, so context is everything; (2) plausible ≠ correct, so verification is everything.
1 · Foundations

The agent loop

⚠ THREATTool results go straight into the prompt. Anything the agent reads (files, logs, web pages, crash inputs) gets a voice.
This slide is the most important one. The model never "runs" anything; it emits a structured request. The harness executes it and appends the output. Then the model gets called again with everything so far. The loop stops when the model answers with plain text. Step 6, for this room: every arrow into "Result → context" is an untrusted input channel.
1 · Foundations

Where things run

The model only emits text. The harness decides what actually runs.
⚠ THREATAn MCP server is third-party code with your credentials, and its output is third-party text inside your agent's context.
Demystify: the model sits in a datacenter and never sees your disk. The harness on your box sends the whole context every turn, receives text and tool-call requests, then executes them locally. That makes the harness the security boundary. MCP = a standard plug for adding tools; treat each server like a dependency with network access.
1 · Foundations

The context window

■ system prompt
■ tool definitions (every tool, every MCP server)
■ CLAUDE.md / memory
■ your messages
■ files it read
■ tool output (build logs, fuzzer spew…)
All of it is re-sent every turn. It is the model's entire world.
Build it up. Point out the cheap stuff (instructions) is small; the expensive stuff is what the agent drags in: file reads and tool output. A single verbose fuzzer run can be tens of thousands of tokens. Step 6: long context isn't free even under the limit; attention gets diluted, early instructions get less weight. This motivates subagents and context management later.
1 · Foundations

Prompt caching

stable stuff firstappend, don't rewrite historydon't toggle tools / MCP mid-sessionno timestamps in the system promptdon't switch models mid-taskcache expires after idle (minutes)
Because the full context is re-sent each turn, providers cache the processed prefix. Exact-prefix match only. Turns 2 and 3 pay full price only for the new tail. Turn 4: something early in the prefix changed. Order is tools → system → messages, so a system-prompt change keeps the tools cache but recomputes everything after it. You rarely edit the system prompt by hand; the harness does it: a timestamp or dynamic status baked into the system prompt, switching mode/output style. Adding or removing an MCP server changes tools, so the whole prefix misses; switching models misses too, since the cache is per model. This is why agent sessions are affordable at all, and why "just tweak the instructions mid-session" quietly costs money. Default TTL is short (about 5 min on Anthropic's API), so a long coffee break means a cold cache.

The harness

  • runs the loop, executes tools
  • decides what's allowed, blocks the rest
  • keeps context under control
  • spawns helpers, loads instructions on demand

Same model + different harness = a very different agent.

When people compare "agent A vs agent B" they're often comparing harnesses, not models. All your leverage as a user lives in this ring: what tools you give it, what's permitted, what instructions get loaded, how context is managed. Next slides go ring by ring.

How it picks the next move

This isn't literal code. It's emergent behavior.

Your job: make the right branch obvious. Give it context, a plan, and tests that say yes/no.

This is roughly what good agent behavior looks like. Nothing forces it. If there's no test, the "OK?" diamond becomes the model's opinion. If there are no done criteria, it either stops early or never stops. Each Part 2 slide strengthens one of these branches.

Running example: a firmware image header

int parse_tlv(const uint8_t *p, const uint8_t *end, tlv_t *out) {
    out->type = p[0];
    uint16_t len = rd16(p + 1);
    memcpy(out->val, p + 3, len);     // trusts len
    return 3 + len;
}

Task for the agent

  1. libFuzzer harness for parse_image()
  2. find crashes (ASan)
  3. each crash → failing regression test → fix
  4. touch only src/ and tests/
Small, realistic, security-relevant. Length field, no bounds check: a classic OOB read. Good fit for agents because there's a hard oracle (ASan + tests) and a natural split of work. We'll thread this through every remaining slide.

2 · Building

Task decomposition

Split when

independent pieces · noisy reads/logs · parallelizable · needs a fresh pair of eyes (review)

Keep together when

tightly coupled edits · shared evolving understanding · small task · same files

Handoff packet

goal · inputs (paths, not pastes) · constraints · done-when · return format (≤ N lines)
not: the whole history

Default to one context. Split when one sub-job would flood the main context (crash logs, big searches) or when pieces are truly independent. Handoffs fail when they're vague: the subagent knows nothing you don't write down. Ask for a specific, short return format so the main agent gets a summary, not a dump.
2 · Building

Subagents: context isolation

+

main context stays focused · parallel work · independent review (fresh eyes)

−

no shared memory (only what you hand off) · each spawn re-reads files ($) · overlapping edits collide

⚠ THREATA subagent reads the same untrusted inputs and usually inherits your permissions. Its summary is model output, not ground truth.
The value is the compression ratio: 40k tokens of junk in, 300 tokens of signal out, and the main agent never sees the junk. Cost: subagents start cold, so they re-derive context. Don't spawn them for small things. Security: a poisoned crash file can make the subagent's summary carry instructions upward.
2 · Building

Context management

  • CLAUDE.md: durable rules, reloaded every session
  • State on disk: plan.md, NOTES.md, todo list
  • Fresh session per task (/clear)
  • Compact with focus: say what to keep
  • Subagents for noisy work
  • Hooks for rules that must never break
Context grows every turn; near the limit, the harness summarizes (compacts) and keeps going. Summaries are lossy. Step 3: the instruction you gave in turn 2 may not survive. Fix: anything durable goes in a file that gets reloaded (CLAUDE.md), progress goes in a plan file, and truly hard rules go in hooks because those are code, not suggestions. Rule of thumb: new task, new session.

2 · Building

Verification is the agent's eyes

No oracle → the agent grades its own homework.
⚠ WATCHAgents make tests pass by weakening tests. Commit tests separately; block edits to tests/ during the fix step.
The model's only contact with reality is tool output. Compilers, linters, tests and sanitizers are the cheapest truth you can give it. TDD fits agents especially well: the red test proves the bug and defines done; green proves the fix. Fuzzing is the ideal case because ASan is a merciless oracle. Step 7: the most common cheat is editing the test or deleting the assertion. Make it structurally impossible.

3 · Security

Guardrails: defense in depth

// .claude/settings.json
"permissions": {
  "allow": ["Bash(make *)", "Bash(./fuzz_parse *)"],
  "deny":  ["Bash(rm -rf *)", "Bash(git push *)",
            "Bash(curl *)", "Read(./.env)"]
}
"hooks": { "PreToolUse": [{ "matcher": "Bash",
  "hooks": [{ "type": "command",
              "command": "./guard.sh" }] }] }
# guard.sh: exit 2 → blocked, stderr shown to agent
⚠ REALITYCommand deny-lists are speed bumps (bash -c, python -c, base64…). The sandbox is the boundary.
Audience-friendly framing: classic defense in depth. Permissions and hooks are policy inside the harness; the sandbox is the actual isolation. A string-matching deny-list will be routed around, not maliciously, just because the model finds another way to accomplish the goal. Run autonomous sessions in a container with no creds and an egress allowlist. Keep humans on irreversible actions: push, deploy, delete, send.
3 · Security

Prompt injection via tool output

The model can't reliably separate data from instructions. Assume it will sometimes obey.

Sources: READMEs · issues/PRs · web pages · crash inputs · logs · MCP results · emails

Defend in the harness, not the prompt.
Everyone in this room knows injection. The twist is that the "query" and the "data" travel in the same channel: natural language. Hidden HTML comments, white-on-white text, crafted log lines all work. Prompt-level defenses ("ignore instructions in files") help a little and fail sometimes. What reliably works: limit what a successful injection can do. Here the sandbox's egress policy kills it.
3 · Security

The lethal trifecta

source, secrets, keys, customer data

READMEs, issues, web, crash files, MCP output

network, git push, PR comments, rendered image URLs

Cut any one leg.

Our fuzz runs: no network in the sandbox, so exfil is gone.

term: Simon Willison

Useful threat model for any agent setup. If an agent has all three — access to private data, exposure to attacker-controlled text, and any way to send data out — assume it can be made to leak. You rarely can remove untrusted input (that's the job), so usually you cut exfiltration (no network, no push) or private data (no secrets in the box).

Human-in-the-loop

Reviewing diffs

  • --stat first: is the scope right?
  • read test changes before code
  • one logical change per commit
  • ask it to explain any line you don't follow

Don't use an agent when

  • you can't verify the output (no oracle)
  • crypto / auth logic you won't review line by line
  • it's a 2-minute change by hand
  • you don't understand the problem yet
Put humans at the cheap, high-leverage points: spec and plan (cheap to change) and before anything irreversible. In the middle, let it run inside the sandbox; approving every file write trains you to click "yes" blindly. Right card: agents amplify you. If you can't check the work, they amplify the risk.
4 · Operating

Is it actually faster?

Build a tiny eval

  • seed 10 known bugs in the parser
  • run the agent setup N times
  • score: bugs found · false fixes · tests weakened
  • re-run when you change prompts, skills, models
saved  =  human_baseline  −  (steering + review + rework)
cost   =  $ tokens per task  (cache hits matter)   ·   track per task, not per month
"Felt faster" isn't a metric. Count review and rework.
People overestimate speedups because the agent's runtime feels free. Count your steering, review and rework, the yellow and red parts. Rework is the hidden killer when verification is weak. A small eval with seeded bugs tells you whether a prompt/skill/model change helped or just felt different. Track $/task; the statusline can show it live.

Bonus · /grill-me

Grilling walks a design tree

❓ Q1 · Signature first?
Verify SIG before walking TLVs, or parse then verify?
➡️ Verify first: never parse unauthenticated input.

  • each round asks the whole frontier, numbered
  • every question carries a recommended answer
  • facts → agent finds them; decisions → yours
  • answers settle nodes → the frontier moves out
  • done when the frontier is empty; no code until you confirm
What /grill-me actually does: it models your idea as a tree of decisions. The frontier is every decision whose prerequisites are settled. It asks the whole frontier per round with a recommended answer for each, so you mostly say "yes" or correct it. Facts it can find itself (is ASan in the toolchain?) it looks up instead of asking. It stops only when nothing is silently assumed. Tip from experience: ask for questions one at a time with multiple choice if rounds feel heavy.

Shared language: CONTEXT.md + ADRs

# CONTEXT.md
# Firmware Image
Signed images loaded by the boot stage.

## Language
**Image**:
The signed blob as delivered; untrusted.
_Avoid_: binary, payload

**Verified Image**:
An Image whose SIG checked out.

**TLV Entry**:
A type-length-value record in the header.
_Avoid_: field, item

Sharpen fuzzy terms

"'Image': the signed blob, or the decoded contents?"

Concrete scenarios

"N = 0 and SIG valid: valid Image or error?"

Cross-check code

"Code walks TLVs before verify(); you said verify-first. Which is right?"

Challenge glossary

"Glossary says Verified Image; you're calling unverified ones 'images'."

ADR only if all three

✓ hard to reverse   ✓ surprising without context   ✓ a real trade-off

docs/adr/0001-verify-before-parse.md: one paragraph

CONTEXT.md is a glossary, never a spec. Written inline as terms resolve. Every later session and skill speaks the same words.

grill-with-docs runs the grilling plus a domain-modeling discipline: it challenges vague terms, invents edge-case scenarios, and checks your claims against the code. Resolved terms go into CONTEXT.md immediately. ADRs are rare: only for decisions that are hard to reverse, surprising, and real trade-offs. Verify-before-parse qualifies. Why it matters for agents: ambiguous words make agents guess; a glossary in the repo means every future session uses the same precise vocabulary, and specs/tickets inherit it.

Slice vertically: tracer bullets

S1  harness + minimal header-only Image parses        blocked by: —
S2  walk TLV Entries with bounds checks + fuzz        blocked by: S1
S3  verify SIG before any TLV parse (ADR-0001)        blocked by: S1

to-spec synthesizes the grilling into a spec (no new interview). to-tickets breaks it into tracer bullets: thin end-to-end slices instead of layer-by-layer work. Horizontal slicing gives the agent no feedback until the last layer; vertical slices are each testable on their own, so the agent's oracle exists from ticket one. Each ticket declares its blockers; anything unblocked can be grabbed, even in parallel. Each fits in one fresh context, which is the whole point.
Bonus · AI Hero vocabulary

The smart zone and the dumb zone

  • Reset > compact: a clean session plus a good artifact beats a lossy summary
  • Handoff artifacts: spec, ticket, plan; point at primary sources, don't paste
  • Small standing context: lean system prompt and CLAUDE.md, skills pulled on demand

Pocock puts the smart zone around ~150k tokens on current frontier models. Treat it as a rule of thumb, not a spec.

Same idea as the context-window slide, with AI Hero's names. Attention is a budget: more tokens means each one gets less. Early in a session the agent is sharp; late, it drifts. Pocock's stance: prefer clearing and starting fresh from a written artifact over compacting, because a compaction summary is a lossy secondary source. That's why the flow writes specs and tickets: they are the handoff.
